# 反思与教训 (Reflections)

从错误和用户反馈中总结的经验教训。每次犯错都是一次学习机会。

---

## 反思 1: "实现了不等于能工作" -- 端到端验证的缺失

### 事件
威胁检测系统看起来代码很完整 -- ThreatEvaluator 有完善的评估逻辑，EmergencyProtocol 有完整的状态机，FileEncryptor/FileWiper 有真实的加密和擦除实现。但实际运行时整个系统是惰性的，因为事件根本没有流入。

### 教训
- **管道比节点更重要**: 每个组件单独看都"实现了"，但组件之间的连接（IPC 注册、线程启动、事件转发）完全缺失。系统的价值在于端到端的流水线，不在于单个零件。
- **必须从用户视角测试**: 而不是从代码视角验证。用户做了一个简单的操作（压缩 50 个文件），系统应该做什么？如果答案是"什么都没发生"，说明有根本性问题。
- **缺少冒烟测试**: 至少应该有一个测试验证"事件从 ETW -> GuardianC -> IPC -> GuardianA -> 评估 -> 响应"这条完整链路。

### 改进
- 创建了 `tests/test_threat_detection.ps1` 端到端测试脚本
- 未来每次修改核心管道逻辑后都应运行此测试

## 反思 2: "为什么不反思！为什么不测试！" -- 用户的愤怒是正确的

### 事件
用户在第一次报告"压缩 50 个文件没有触发紧急协议"后，我给出了一些可能的原因。用户追问"什么时候触发日志！什么时候加密！什么时候删除！你清楚吗！"。这说明我在给出代码之前没有真正理解自己写的系统是如何工作的。

### 教训
- **自己不清楚的东西不要交给用户**: 在实施之前应该画出完整的数据流图，确认每一步都有代码支撑
- **被问到"你清楚吗"说明沟通失败了**: 应该主动、提前、清晰地说明系统行为，而不是等用户追问
- **反思不是可选的**: 在实现复杂功能后，应该主动审查所有相关路径，而不是认为"写完了就完了"

### 改进
- 本次重构中进行了全面审查，发现了 NotificationManager Session 0 问题和 GuardianB 不一致问题
- 创建了 `threat_detection_design.md` 明确记录所有行为规则

## 反思 3: 功能实现后必须验证运行环境 -- Session 0 的教训

### 事件
`NotificationManager` 的通知功能在开发和单元测试环境中可能看起来正常，但在实际部署环境（Windows 服务 Session 0）中完全失效。这个问题直到全面审查时才被发现。

### 教训
- **Windows 服务的 Session 0 隔离是基本常识**: 服务无法创建窗口、访问剪贴板、显示 UI。任何依赖这些能力的代码在服务中都会静默失败。
- **"静默失败"是最危险的**: `GetDesktopWindow()` 返回 NULL 但不报错，`NotificationManager` 初始化时不会崩溃但通知永远不会显示。
- **安全系统的告警通路必须有冗余验证**: 如果用户看不到告警，威胁就是隐形的。

### 改进
- 告警改走 IPC 路由，从架构上保证通知到达用户桌面
- GuardianA 和 GuardianB 的 `SendAlert` 都统一使用 IPC 路径

## 反思 4: Windows 批处理脚本是一个雷区

### 事件
`uninstall.bat` 经历了 4 轮修复。每次都以为修好了，但用户运行后又发现新问题。

### 教训
四个必须遵守的规则:
1. **行尾必须是 CRLF**: `cmd.exe` 严格要求 `\r\n`。如果编辑器保存为 LF，脚本会"闪退"
2. **不能有 UTF-8 BOM**: `EF BB BF` 字节前缀会被当作 `@echo off` 的一部分，导致 echo off 失败
3. **用 `REM` 注释，不用 `::`**: `::` 是无效标签，在 `chcp 65001` (UTF-8 代码页) 下，后续的中文字符会被当作命令执行
4. **不要用 `exit /b 1` 做错误处理**: 这会终止整个脚本，后续的清理逻辑不会执行。应该用错误标记 + 最终统一退出

### 改进
- 所有批处理脚本编写时遵循上述 4 条规则
- 如果可能，优先使用 PowerShell (.ps1) 替代批处理

## 反思 5: 代码复制导致行为分歧 -- GuardianB 的教训

### 事件
GuardianB 有自己独立的 `AssessThreat()` 和 `ExecuteResponse()` 实现，是从 GuardianA 早期版本复制过来的。当 GuardianA 的逻辑被重新设计后，GuardianB 的行为与之完全不同 -- 它仍然会对单事件执行 ENCRYPT 和 WIPE。

### 教训
- **复制粘贴是技术债的入口**: 两份"几乎相同"的代码，维护一份时另一份必然落后
- **共享代码应该共享源码，而非复制**: 通过 CMakeLists.txt 引入相同的 .cpp 文件，或抽取到公共库
- **GuardianB 的角色需要明确**: 它是"备份"，不是"独立决策者"。在 backup 模式下只需要转发

### 改进
- GuardianB 现在直接引用 GuardianA 的 `threat_evaluator.cpp`
- backup 模式只转发事件，不做评估
- primary 模式复用相同的 ThreatEvaluator 类和阈值配置

## 反思 6: 对用户反馈的响应速度决定信任

### 事件
uninstall.bat 的问题用户报告了多次。每次我说"已修复"，用户运行后又出问题。这严重损害了用户的信任。

### 教训
- **"修好了"必须经过自己的验证**: 不能只改代码就说修好了，应该在目标环境（或尽可能接近的环境）验证
- **如果无法直接验证，要诚实说明**: "我已经按照分析修改了代码，但我无法直接在你的环境运行。请你测试后告诉我结果"
- **多次失败后应该暂停，系统性地排查**: 而不是逐个修一个看一个。第 4 轮修复之前应该一次性检查所有可能的 cmd.exe 兼容性问题

## 反思 7: "改了 A 忘了 B" -- 变更传播的系统性失败

### 事件
`file_copy` 重命名为 `file_write`，代码和 YAML 配置已更新，但 10 个文档文件仍然使用旧名称 `file_copy_count`。GuardianA 的 AssessThreat 重新设计后，GuardianB 的 AssessThreat 仍然保持旧行为——FILE_DELETE 只是 LEVEL_1、FILE_COMPRESS 缺少 BLOCK、PROCESS_INJECT 缺少 TERMINATE。更讽刺的是，"对齐 GuardianB"在上一轮已经作为明确的修复目标被执行过，但仍然遗漏了 3 处差异。

### 错误方法
聚焦"主要文件"（代码本体），把文档和"备份组件"当作"后续清理"。修完主要文件后产生"完成感"，注意力转移到下一个任务。对齐 GuardianB 时，只修改了"最明显的差异"（FILE_NETWORK_TRANSFER 的 ENCRYPT+WIPE），没有逐行比对。

### 正确方法
在动手修改之前，先执行 `rg "旧关键词"` 枚举所有引用点。建立"变更清单"，逐项确认每个引用点都已更新后才标记为完成。对齐两个文件时，使用 diff 工具逐行比对，而非凭印象修改。

### 根本逻辑
这是**注意力管理失败**。人的注意力天然聚焦于"最难的部分"，而变更传播属于"机械性工作"，容易被认知资源跳过。解决方案不是"更仔细"（因为人的注意力本质上有限且不可靠），而是**用工具替代注意力**——用搜索代替记忆，用清单代替意愿，用 diff 代替"我觉得一样了"。

### 改进
- 本轮使用 `rg "file_copy_count"` 发现 10 个文件 28 处遗漏引用
- 全部替换后再次 `rg` 确认结果仅剩 config.cpp 的向后兼容别名
- 建立规则：任何"重命名"操作后，必须 grep 验证旧名称出现次数为 0

## 反思 8: "修了 4 轮还没修好" -- 增量修补的恶性循环

### 事件
uninstall.bat 经历了 4 轮修复（LF→CRLF、BOM、:: 注释、逻辑错误），每轮我都说"已修复"，用户运行后又发现新问题。GuardianB 在上一轮"对齐"后仍有 3 处差异。这不是偶然——它是**同一种错误模式的反复呈现**。

### 错误方法
用户报告问题 → 找到一个原因 → 修复这个原因 → 宣布修好。这是**症状驱动的修复**，每次只消除一个症状，不检查是否有其他同类问题。

### 为什么会反复犯
找到第一个原因后产生**确认偏误**——"我找到了原因"这个认知满足感会阻止进一步探索。修复后看到"改动生效"更加强化了"问题已解决"的信念。这是人类认知的结构性缺陷：**大脑倾向于在找到第一个合理解释后停止搜索**，即使可能存在更多问题。

### 正确方法
找到第一个原因后，**强制停下来问"还有什么？"**：
- 对 cmd.exe 批处理：一次性枚举所有已知陷阱（行尾格式、BOM、注释语法、变量展开、错误处理、编码、特殊字符转义）
- 对 GuardianB 对齐：逐行比对两个文件的同名函数，逐 case 确认 level、action、description 三者完全一致
- 对任何修复：修复前花 10 分钟枚举所有可能的同类问题，比修一个看一个总耗时更短

### 根本逻辑
这是**局部最优陷阱**。每次修一个点是局部最优（最快消除当前症状），但全局最劣（总修复次数最多，用户信任受损最大）。跳出局部最优的方法是**延迟行动、扩大搜索**——花 10 分钟枚举所有可能的问题，比立刻修第一个问题然后再修 3 轮，总耗时更短，总信任损失更小。

### 改进
- 本轮在修复前先完成全面审查（发现 4 个代码问题 + 5 类文档问题），一次性修复
- 建立规则：发现任何 bug 后，先问"还有没有同类 bug"，用搜索工具验证后再动手修复

## 反思 9: "看起来完成了" vs "验证完成了" -- 确认偏误的深层根源

### 事件
威胁检测系统代码"看起来完整"但完全不工作（事件管道断裂）。文档"看起来已更新"但 10 个文件未同步。GuardianB"看起来已对齐"但 3 处差异。YAML 注释"看起来正确"但描述的行为与代码完全不符（"网络传输 → 触发紧急协议"而实际是 BLOCK）。

### 错误方法
写完代码/改完文档后，通过**阅读自己写的代码**来验证。但这等于"用写错答案的同一个大脑去检查答案"——检查者和出错者是同一人，自然看不出错误。更深层的问题是：我把"我知道这段代码应该做什么"等同于"这段代码确实在做这件事"。

### 为什么明知有错还改不好
因为每次"修复"后的验证方式没有变——依然是"看一看觉得对"。如果验证方式不变，每次修复只是碰运气修对了一个，其余的错误依然隐藏。

### 正确方法
用**独立于编写过程的方式验证**：
- **代码**: 不要"看"，要"跑"（运行测试）或"搜"（grep 确认所有引用点）
- **文档**: 不要"想起来改了哪些"，要"搜索所有旧关键词确认为零"
- **一致性**: 不要"觉得 B 和 A 一样了"，要"diff 两个函数确认每行都对齐"
- **注释**: 不要"觉得注释正确"，要"对照代码中实际的 switch-case 表重写注释"

### 根本逻辑
人的认知系统有两种模式：（1）生成模式（写代码、做修改）；（2）验证模式（检查正确性）。大多数情况下，生成模式结束后会直接跳过验证模式，或用生成模式伪装成验证模式（"我觉得改对了"）。真正的验证必须使用**外部工具和独立证据**，而非内心的"感觉"。

验证的核心原则：**如果你只用了眼睛（阅读），你还没有验证。如果你用了工具（grep、diff、测试），你才开始验证。**

## 反思 10: 方法论总结 -- 从错误中提炼的操作规程

### 核心洞察
所有错误都不是因为"不认真"或"不够聪明"。它们是因为**试图用不可靠的人类注意力来完成需要机械精确性的任务**。解决方案不是"下次更仔细"（这是一个永远无法兑现的承诺），而是**用正确的流程和工具替代不可靠的注意力**。

### 操作规程

**变更前（延迟行动、扩大搜索）**:
1. `rg "关键词"` 枚举所有引用点 → 建立变更清单
2. 如果发现了一个 bug，先问"还有没有同类 bug"再动手修
3. 列出目标环境的所有约束条件（Session 0 限制、cmd.exe 要求等）

**变更中（按清单执行、不跳过）**:
4. 按变更清单逐项修改，不跳过任何一项
5. 对齐两个组件时使用 diff，不凭印象

**变更后（独立验证、工具驱动）**:
6. `rg "旧关键词"` 确认出现次数为 0（或仅剩有意保留的别名）
7. diff 确认对齐的函数每行一致
8. 运行测试确认行为正确

**声明修复前（诚实透明）**:
9. 明确列出"我验证了什么"（用了什么工具、看了什么结果）
10. 明确列出"我无法验证什么"（需要用户在目标环境测试）

### 背后的根本逻辑

所有反思指向同一个根因：**局部思维 vs 系统思维**。

- **局部思维**: 修一个 bug → 宣布修好。改一个文件 → 忘了其他文件。看一遍代码 → 以为正确。
- **系统思维**: 修一个 bug → 搜索所有同类 bug → 全部修完 → 搜索确认为零 → 才宣布修好。

从局部思维跳到系统思维，不是靠"意愿"（"下次更仔细"），而是靠**流程**（搜索 → 清单 → 执行 → 验证）和**工具**（grep/diff/test 替代眼睛/记忆/感觉）。

### 这些教训的适用范围

这不仅适用于 GuardianShield 项目。它适用于所有需要一致性和正确性的工程工作：
- **代码重构**: 重命名后 grep 确认旧名称为零
- **API 变更**: 搜索所有调用点，不凭记忆
- **配置修改**: 对照代码行为重写注释，不凭"上次的理解"
- **多组件系统**: 修改一个组件后，逐一比对所有使用相同逻辑的组件

## 反思 11: "知道"不等于"做到" -- 约束导向 vs 功能导向

### 事件
`uninstall.bat` 第 5 轮修复。上次重写该脚本添加 MSI 卸载功能时，重新引入了第 1 轮就发现的 `EnableDelayedExpansion` 问题，又新增了 `for /f` 嵌套 powershell 导致 cmd.exe 解析崩溃，以及条件式 `pause` 让用户传参运行时窗口闪退。而这一切的教训早在反思 4、反思 8、行动清单第 4 条中白纸黑字写着。

### 错误方法
"功能导向"重写——关注"要实现什么功能"（MSI ProductCode 查询），直接用自己训练记忆中的"标准写法"（`EnableDelayedExpansion` + `for /f` 嵌套 powershell），完全没有在重写前查阅 memory 中的已知规则。写完后也没有对照 batch 脚本禁区清单逐条检查。

### 为什么会犯已经记录过的错
知识的**存在**不等于知识的**使用**。memory 文件的价值取决于是否在**正确的时间点**被读取。如果写代码时不去查它，它就是一份从未打开的保险单。更深层的原因：重写时的认知模式是"生成模式"（尽快产出可工作的代码），此时大脑默认走"最熟悉的路径"而非"最安全的路径"。要打断这个默认行为，需要强制流程——**先读约束，再写代码**。

### 正确方法
"约束导向"重写：
1. 写任何 batch 代码之前，先读 `memory/reflections.md` 和 `memory/issues_and_fixes.md` 中的 batch 相关条目
2. 将所有禁区列成清单（CRLF、无 BOM、REM、无 EnableDelayedExpansion、无 for/f+powershell、无条件 pause）
3. 在禁区之内设计实现方案（如用 `reg query` + `findstr` 代替 powershell，用 `call :label` 代替 `!VAR!`）
4. 写完后用诊断脚本逐条验证所有约束

### 根本逻辑
所有反思都在说"用工具替代注意力"，但这条规则本身也需要一个触发机制来确保被执行。否则"用工具替代注意力"这条规则本身就沦为另一个需要注意力才能记住的规则——无限递归。打破递归的方法是**把规则嵌入流程**：在任务类型（batch 脚本）和操作（读 memory）之间建立硬连接，而不是靠"记得要这样做"。

## 反思 12: "为什么不主动记录？" -- 任务完成定义的缺陷

### 事件
第一性原理分析中完成了 5 项修复（DriverClient 双份消除、Config 阈值语义、缓存路径统一、GuardianC 托盘文档、encrypt_timeout 确认），但没有一项被正式记录到 memory 的 changelog 或 issues_and_fixes 中。用户追问后才补录了 uninstall.bat 第 5 轮修复，其余 5 项仍遗漏。用户再次追问："为什么不主动记录？为什么要我提醒？"

### 错误方法
将"更新 memory"视为可选的后续清理，而非任务定义的一部分。代码改完 → 产生"完成感" → 注意力转移到下一个任务 → memory 被遗忘。这与反思 7（"改了 A 忘了 B"）是完全同构的问题，只是这次 A = 代码修改，B = memory 记录。

### 为什么会反复犯
因为"完成"的定义是错的。我把"代码能工作"当作任务终点，但真正的终点应该是"代码能工作 AND 变更被记录 AND 文档已同步"。由于 memory 更新不会导致编译错误或运行失败，它在认知优先级中被自动降级为"不紧急"，然后被遗忘。

### 正确方法
任务的完成条件不是"代码改好了"，而是"代码改好了 AND memory 记录了"。这两步是**原子操作**，不可分割。就像 git commit 包含 message 一样——没有 commit message 的提交不算完成，没有 memory 记录的修复不算完成。

### 根本逻辑
这是反思 10 中"用流程替代注意力"原则的又一次验证：不能靠"记得要更新 memory"（注意力），而要把 memory 更新**写入行动清单作为硬性步骤**。每个 todo 标记"完成"之前，必须检查 memory 三件套（changelog、issues_and_fixes、current_state）是否需要更新。

## 反思 13: "修正"反而改错了方向 -- 混淆名称与真名混淆

### 事件
上一轮测试中，服务无法通过 `sc query GuardianA` 查询（因为 MSI 注册的服务名是混淆后的 `WinDefenderCore`/`WinDefenderHelper`）。当时的"修正"是把测试脚本中的 `WinDefenderCore` 改成 `GuardianA`，并手动用 `sc.exe config GuardianA binPath=...` 注册了错误的服务名。测试报告还写下了"服务名不匹配：代码中 WinDefenderCore/WinDefenderHelper，实际注册为 GuardianA/GuardianB"这一**完全错误的结论**。

### 错误方法
观察到"sc query WinDefenderCore 没有结果" → 假设"WinDefenderCore 不是正确的服务名" → 用 `GuardianA` 替代。但没有去验证 WiX 安装器（`GuardianShield.wxs`）中实际注册的 `ServiceInstall Name="WinDefenderCore"`。结果把正确的名称改成了错误的，并且在报告中记录了错误的结论，污染了后续所有人的认知。

### 为什么会犯
1. **先入为主**：项目内部代号是 GuardianA/B/C，代码目录也以此命名，心智模型默认"服务名 = 目录名"
2. **没有追溯真相源**：服务名的唯一真相源是 WiX `.wxs` 文件中的 `ServiceInstall Name=`。当 `sc query` 结果与预期不符时，应该去查 `.wxs`，而不是改测试脚本去适配错误的假设
3. **上次 sc query 可能失败的真实原因**：可能当时 MSI 没有正确安装（之前有多次安装失败的记录），或者 PowerShell 中 `sc` 被解析为 `Set-Content` 而非 `sc.exe`

### 正确方法
遇到"名称不匹配"时：
1. 找到**唯一真相源**（WiX 的 `ServiceInstall Name=`）确认正确名称
2. 用 `sc.exe query <正确名称>` 验证（注意 PowerShell 中必须用 `sc.exe` 而非 `sc`）
3. 如果查不到服务，问题在于安装过程，不在于名称本身

### 根本逻辑
这是**修复方向错误**的典型案例：当现实与模型不符时，应该修正模型（"我对服务名的理解是错的"），但实际上修正了现实（"把服务名改成我以为的样子"）。更糟糕的是，把错误结论写进了报告，形成了**错误知识的持久化**。验证任何名称/路径/配置时，必须追溯到代码或安装器中的定义，不能凭内部代号推测。

### 改进
- 项目组件真实名称映射表（已建立）：

| 内部代号 | 服务名 | 显示名 | 可执行文件 | 启动方式 |
|---------|--------|--------|-----------|---------|
| GuardianA | `WinDefenderCore` | Windows Defender Core Service | `svchost_core.exe` | Windows 服务 |
| GuardianB | `WinDefenderHelper` | Windows Defender Helper Service | `svchost_helper.exe` | Windows 服务 |
| GuardianC | _(无服务名)_ | `WindowsMonitor` (注册表键) | `winmon.exe` | 注册表 Run 自启动 |

## 反思 14: 恶性循环的根因——代码架构在制造错误，反思系统在制造幻觉

### 事件
项目经历了 13 轮反思、20 条行动清单、5 轮 uninstall.bat 修复、3 轮 GuardianB 对齐。每轮反思都精准诊断了问题，提出了正确的解决方案。但同类错误持续复现。用户追问"为什么反复修不好"，要求用第一性原理分析恶性循环本身的根因。

### 逐行代码验证发现的事实
1. GuardianA 和 GuardianB 之间有 **20+ 个重复函数**（HandleDriverEvent、AssessThreat、ExecuteResponse、TriggerProtectionProtocol 等）。甚至 `ThreatAssessment` 结构体都被复制为 `ThreatAssessmentB`，4 个字段完全相同。
2. 3 轮"对齐"后，GuardianB 仍有 **8 处分歧**：缺少 4 层过滤、事件处理顺序颠倒、ThreatEvaluator 缺 file_create 阈值、ExecuteResponse 重复日志、TriggerEmergencyProtocol 行为不同。
3. 反思 5 说"共享代码应该共享源码"，但只共享了 1 个文件（ThreatEvaluator），其余 19 个函数仍然是复制品。
4. 行动清单第 10 条说"用 diff 逐行比对"，但 3 轮对齐中**从未实际执行 diff**。
5. 行动清单第 13 条说"重写 batch 前先读 memory"，但第 5 轮修复中**未查阅 memory**。

### 根因分析：三层递进

**第一层（表面）**：没有遵守规则。

**第二层（结构）**：规则储存在被动文本中（reflections.md），必须被主动打开并阅读才能生效。但打开它的时机本身需要记忆力——而整个问题的根因就是记忆力/注意力不可靠。这是一个**递归悖论**：用有缺陷的工具（注意力）修复自身的缺陷（注意力不足）。

**第三层（根本）**：代码架构本身在持续制造"需要人工保持一致"的场景。20 个重复函数 = 每次修改创造 1 次犯错机会 + 1 次遗忘机会。这不是通过"更仔细"能解决的——这是数学上的必然。只要重复存在，分歧就会持续产生。

### 为什么 20 条行动清单不管用

行动清单从第 1 条到第 20 条，每条都在说"做完 X 后要做 Y"。但"要做 Y"本身是一个需要记住的规则。当规则数量从 1 增长到 20 时，漏掉任意一条的概率在增长，而不是在减少。**更多的规则 = 更高的遗忘概率**。

### 正确方法：结构性消除，而非规则性约束

1. **提取共享基类 GuardianCore**：将 20 个重复函数放在一个地方。修改一处，两处同时生效。"改了 A 忘了 B" 这个问题类别直接消失。
2. **自动化验证脚本 verify.ps1**：不靠"记得要验证"，靠运行一个命令即可。
3. **每次对话开始时强制读取 memory**：通过 .cursor/rules 硬编码为 AI 行为规则，而非依赖 AI 自觉遵守。

### 根本逻辑
所有反思（1-13）都在说"用工具替代注意力"。但反思系统本身（reflections.md + 行动清单）仍然依赖注意力来触发。这是一个**元层面的同构问题**：反思系统用于修复注意力缺陷，但反思系统的使用本身需要注意力。打破方式：不用"被动文本"（需要主动查阅），用"主动机制"（自动执行，不需要记住）。

### 根本逻辑

## 反思 23: 假设驱动诊断 vs 证据驱动诊断 — ETW 根因误判的教训

### 事件
v2 修复方案（IPC 通知可靠性修复）的推理链：用户报告"没看到通知" → 假设 ETW 检测正常 → 诊断 SendToNode 线程安全 → 修复 mutex。但该假设从未验证。实际上 GuardianA 日志在 15:45:05 后停止更新，ETW 采集线程 CPU 为 0——事件根本没有被检测到。如果在修复前执行一次日志检查（`Select-String guardian_a.log -Pattern "FILE_WRITE"`），就会立即发现日志无文件事件，从而将注意力聚焦到 ETW 层。

### 为什么会犯
1. **诊断起点偏移**: "通知没弹出"自然引导到"通知系统有问题"，而非"事件采集有问题"。未从最底层（ETW 是否在工作？）开始逐层排查
2. **自审框架锁定**: v2 的自审问的是"这个 IPC/通知修复方案对不对？"而非"我在修复正确的层吗？"——自审未跳出既定框架
3. **验证层次不足**: "cmake PASS + ctest 162/162 PASS"只证明编译和单元测试通过，不证明运行时行为正确。真正的验证是部署→触发文件事件→检查全链路日志

### 正确方法
诊断必须从**最底层**开始向上排查：
1. ETW 回调是否触发？（检查 `etw_thread.txt` / 线程 CPU）
2. 事件是否被正确分类？（检查 GuardianA 日志中的事件类型分布）
3. 评估是否产生正确动作？（检查 AssessThreat 输出）
4. IPC 消息是否送达？（检查 SendToNode 日志）
5. 通知是否显示？（检查 ShowBalloonNotification 返回值）

每一层确认正常后才进入下一层。

### 行动项
39. **诊断任何"功能不工作"问题时，必须从数据源（ETW/驱动/输入）开始逐层向上排查**，不能跳过中间层直接诊断末端
40. **"编译通过 + 单元测试通过" ≠ "运行时行为正确"**。修复方案的验证必须包含运行时证据（日志、进程状态、管道连通性），不能仅依赖编译器
41. **自审必须质疑前提假设**：在审查具体修复方案之前，先问"我是否在修复正确的层？前提条件是否经过验证？"

## 反思 26: "文件会被安装" ≠ "安装的是正确版本" — MSI 升级配置毁灭链

### 事件
简化 MSI 安装流程时，移除了 `CA_CopyConfigFiles`（自定义动作）。方案验证时确认"WiX File 元素仍自动部署配置文件，描述仍成立"——只验证了**文件会被安装**，没有追踪**安装的是哪个版本的文件**，更未追踪 MajorUpgrade 对 `config_cache.bin` 的毁灭性影响。

结果：MajorUpgrade 执行时，旧产品的 `RemoveFile`/`RemoveFolder` 摧毁了 `config_cache.bin`（含已缓存的合法授权条目）和旧的 `auth.list`。新产品部署了默认的 `auth.list`（含开发环境硬编码 IP/MAC）。重启后服务加载默认授权列表，但**开机时网络适配器尚未就绪**（IP 未分配），两次授权检查（含 2 秒重试）均失败，触发 Tier-2 不可逆紧急协议——文件加密、原件擦除、服务停止心跳。

### 5 步连锁故障链
1. MajorUpgrade → RemoveExistingProducts → 旧 config_cache.bin 被删除
2. 新 MSI 部署默认 auth.list（开发环境 IP/MAC）
3. 服务启动时网络未就绪 → IP 未分配 → ValidateEnvironment 两次都失败
4. HasAuthorizationList()=true → TriggerEmergencyProtocol(skipAlert=true) → 文件加密+擦除
5. OnStart return → 工作线程未启动 → 无心跳 → GuardianC 报服务不响应

### 教训
- **配置文件有"版本"**：默认配置（打包在 MSI 中）和用户配置（运行时生成/自定义）是完全不同的东西。移除自定义部署逻辑后，必须追踪"默认配置在目标环境是否合理"
- **MajorUpgrade 是一次"卸载+安装"**：旧产品的所有清理逻辑（RemoveFile、RemoveFolder）会在新产品安装前执行。如果旧产品清理了某个关键文件，而新产品依赖该文件，就形成了"升级陷阱"
- **开机时网络不可靠**：服务启动时（特别是 AUTO_START 服务），网络适配器可能尚未就绪。2 秒重试不够，特别是冷启动时 DHCP 分配 IP 可能需要 5-15 秒
- **auth.list 默认内容不应包含任何实际 IP/MAC**：空列表 → 安全模式（良性），硬编码列表 → 不匹配时触发紧急协议（致命）
- **"验证文件会被安装"只完成了验证的 1/3**：完整验证需要 (1) 文件是否安装 (2) 安装的是哪个版本 (3) 该版本在目标环境是否有效

### 修复
1. 默认 `config/auth.list` 改为仅含注释的空文件 → 新安装进入安全模式而非紧急协议
2. 添加 `CA_BackupConfigCache`/`CA_RestoreConfigCache` 自定义动作 → 在 RemoveExistingProducts 前后备份/恢复 config_cache.bin
3. 将 `CA_BackupConfigCache` 调度在 `Before="CA_SetDefaultKey"`（RemoveExistingProducts 之前），`CA_RestoreConfigCache` 调度在 `After="RemoveExistingProducts"`

### 行动项
45. **移除或替换任何配置部署逻辑时，必须追踪：(a) 默认配置内容是否在所有目标环境有效 (b) MajorUpgrade 是否会摧毁运行时配置 (c) 升级后服务首次启动时的网络/环境状态**
46. **默认配置文件不应包含环境特定数据**（IP、MAC、路径等）。这类数据应由管理员部署或首次运行时生成
47. **安全系统的授权检查必须能容忍启动时网络未就绪**：空授权列表应进入安全模式（监控但不触发紧急措施），而非触发最严格的紧急协议

## 反思 27: "0.0.0.0 跳过" — 一行代码的致命设计缺陷与三层防御

### 事件
反思 26 的修复（CA_BackupConfigCache + 2s 重试）部署后，冷启动问题**再次复现**：服务 3:35:10 启动，3:35:12 文件被加密——2 秒延迟精确匹配 `Sleep(2000)` 的单次重试。auth.list 和 config_cache.bin 均已正确保留，但服务仍然判定"未授权"并触发 Tier-2 紧急协议。

### 根因（深层）
`EnvironmentValidator::GetAllNetworkInterfaces()` 第 248 行：`if (ip != "0.0.0.0") { interfaces.push_back(...); }`——冷启动时 DHCP 未完成，所有网络适配器 IP 都是 "0.0.0.0"，该条件导致函数返回**空列表**。而 MAC 地址（硬件地址）在任何时候都可用。

`IsAuthorized()` 要求 IP + MAC 同时匹配。空列表 → 没有任何接口可供匹配 → `ValidateEnvironment()` 返回 false。即使 fallback `GetCurrentIPAddress()` 也返回 "0.0.0.0"，依然不匹配 auth.list 中的任何条目。

### 为什么前一次修复没有发现
1. **只治标不治本**：Sleep(2000) 试图等网络就绪，但 DHCP 可能需要 5-30 秒
2. **未追踪数据流**：验证了 config_cache.bin 被保留，但没有追踪 `GetAllNetworkInterfaces()` 在启动瞬间返回什么
3. **"0.0.0.0 跳过"是初始设计时写死的过滤逻辑**，没有考虑冷启动场景。之前所有测试都在网络已就绪的环境下进行

### 三层防御修复
1. **Layer 1（根本修复）**：`GetAllNetworkInterfaces()` 移除 "0.0.0.0" 跳过逻辑，让 MAC 始终可用；`IsAuthorized()` 在 IP 为 "0.0.0.0" 时视为通配符（仅靠 MAC 匹配）。安全性分析：攻击者无法将自己的 IP 设为 "0.0.0.0"，MAC 仍精确匹配
2. **Layer 2（安全网）**：`ValidateEnvironment()` 从 Sleep(2000)+1 次重试改为 10 次 × 3 秒智能重试，区分"有真实 IP 但不匹配"（立即失败 = 真正未授权）和"无真实 IP"（继续等 = 网络未就绪）。有了 Layer 1 的 MAC-only 降级，Layer 2 几乎不会被触发
3. **Layer 3（安装器层）**：WiX `ServiceInstall` 添加 `<ServiceDependency Id="Tcpip" />`，让 SCM 在 TCP/IP 协议栈就绪后才启动服务

### 教训
- **过滤逻辑必须考虑边界值**：过滤 "0.0.0.0" 看似合理（"无效 IP"），但在冷启动场景下，这是唯一的 IP，过滤掉就等于丢弃了 MAC 信息
- **MAC 地址是硬件属性，IP 地址是协议属性**：在需要硬件级身份验证的场景，不应因协议层未就绪而丢弃硬件层信息
- **修复必须追踪到数据源**：不能只验证"配置文件在不在"，还要验证"运行时函数返回了什么值"
- **"增加等待时间"不是修复网络未就绪的正确方法**：正确做法是利用已有信息（MAC）和声明依赖（ServiceDependency）

### 行动项
48. **网络相关的校验函数在设计时必须考虑 DHCP 未完成场景**：IP 为 "0.0.0.0" 不应被视为"无效"而丢弃，应被视为"尚未分配"并降级处理
49. **安全校验应区分"无法验证"和"验证失败"**：前者应重试或降级，后者应立即触发安全响应
50. **修复启动时序问题时，"增加等待"只是权宜之计**：正确做法是声明依赖（ServiceDependency）+ 利用已有信息（MAC）+ 智能重试（区分场景）

## 反思 28: ALERT 自动恢复的竞态 — 不审计就实施 = 埋雷

### 事件
v2.9 改进方案初版将 ALERT 15 秒自动恢复放在 Phase 1（纯 UI 改动）。深度审计后发现：GuardianA 的 Tier-1 倒计时默认 30 秒（可配置更长），如果 GuardianC 在 15 秒后自动将托盘恢复为绿色，而 GuardianA 仍在倒计时中，用户会看到绿色托盘误以为安全，实际上加密随时可能触发。

### 教训
- **UI 状态必须反映真实系统状态**：GuardianC 的托盘颜色不是独立的 UI 属性，它代表的是 GuardianA 的紧急状态。任何"自动恢复"必须基于 GuardianA 的真实状态，而非猜测的超时时间。
- **跨组件的状态同步需要正式协议**：不能靠 C 端猜 A 端的状态，必须有 A→C 的状态通知消息（STATE_SYNC NORMAL）。
- **审计不是可选的额外步骤**：如果直接实施初版方案，这个竞态在正常测试中不会被发现（因为大多数情况 Tier-1 倒计时会在 30 秒内完成），但在实际攻击场景中会成为致命的安全误导。

### 修复
将 ALERT 恢复移到 Phase 2，实现双端同步：A 端取消倒计时后广播 STATE_SYNC(NORMAL)，C 端收到后才恢复绿色，加上 120 秒（2×默认倒计时）时间兜底作为最后安全网。

### 行动项
51. **任何影响安全状态显示的 UI 改动，必须追溯到状态源头确认正确性**：不要靠客户端猜测服务端状态。
52. **跨组件状态同步优先使用消息通知而非超时猜测**。

## 反思 29: 单元测试的环境副作用 — ACL 锁定文件阻止 TearDown 清理

### 事件
T5 (KeepLocksWhenFlagSet) 测试在首次运行时 PASS，但后续重跑时 FAIL。原因：T5 测试故意保持文件 ACL 锁定（验证 `m_keepLocksOnDestroy=true`），但 TearDown 的 `std::filesystem::remove_all()` 无法删除 ACL 保护的文件。下次运行时 SetUp 发现目录已存在，内含旧的 ACL 锁定文件，新的 LockFile 调用因权限被拒绝而失败。

### 教训
- **测试中改变系统级状态（ACL/注册表/服务）必须有对称的清理逻辑**
- **`std::filesystem::remove_all` 不能处理 ACL 保护的文件** — 需要先用 `SetNamedSecurityInfoW` 重置 DACL
- **单元测试必须是幂等的**：不管之前运行的结果如何，重新运行都应该从干净状态开始

### 修复
在 SetUp 和 TearDown 中添加 `ResetDirectoryAcls()` 辅助函数，使用 `SetNamedSecurityInfoW` 重置目录内所有文件的 DACL。

### 行动项

## 反思 32: 深度审计挽救了 BLOCK 实现 — 先审后做的价值

### 事件
用户要求实现内核级 BLOCK 响应动作以阻止文件移动。初始方案看似简单（加个 IOCTL + 回调检查），但在用户挑战"杜绝交付焦虑，用代码说话"后进行深度审计，发现了 8 项代码问题 + 6 项风险：
1. **2 项致命预存在 Bug (F1/F2)**: GuardianB 驱动连接用错端口名、保护路径不同步 — 如果不修复，BLOCK 在 failover 后完全失效
2. **1 项致命数据模型错误 (F3)**: 方案中假设 `wp.canRead` bool，实际是 `vector<wstring>` — 方案代码会编译失败
3. **自阻塞风险 (RISK-1)**: Guardian 自身的加密/擦除操作会被自己的 BLOCK 策略拒绝 — 紧急协议完全失效
4. **双重惩罚 (RISK-4)**: BLOCK+TERMINATE 同时配置时操作被阻止的同时进程还被杀死

### 教训
- **"先做再说"的代价可能是灾难性的**: 不做审计直接实现，至少 F1/F3 会导致编译失败或运行时崩溃，RISK-1 会导致紧急协议失效
- **新功能不只是新代码**: BLOCK 看似只改驱动回调，实际需要修改 13 个文件、处理 A/B 对称性、驱动重连恢复、白名单同步等
- **预存在 Bug 在新功能中暴露**: F1/F2 之前不是问题（驱动本身就未启用），但 BLOCK 让这些 Bug 变得致命
- **用户的"杜绝交付焦虑"挑战是正确的**: 没有这个推力，可能直接提交有致命缺陷的实现

### 行动项
62. **跨组件功能必须做影响分析**: 新功能接入已有架构时，检查所有相关路径（A/B 对称性、failover、重连、白名单）
63. **数据模型假设必须验证**: 编写 API 调用前先确认实际数据结构（grep 实际 struct 定义）
64. **预存在 Bug 清单要在新功能中重新审视**: 休眠的 Bug 可能被新功能激活
65. **"先审后做"写入内核级功能开发流程**: 驱动 + 用户态联动的功能不能跳过审计阶段
